# Step 5：先核查扫描、距离和候选复用

日期：2026-10-26。用户要求：“如果继续研究这一方向，应先判断能否复用初次扫描、
距离计算或候选结果，消除重复开销。否则，即使预测器准确且免费，也无法弥补这笔成本。”

这是L1源码/已有记录审查，不是新检索协议或实现批准。审查基线为
`e29a9bd957e95b993efb923c357f05d804a88203`。本轮没有新检索、拟合、服务器运行或
保护角色访问；既有实验输出和成本筛查JSON保持原样。

## 结论和前一轮结论的范围

**先检查复用，再评估付费预测器，顺序应如此。现有精确流水线已经复用一次扫描；
HNSW已经复用候选的外部距离，但没有复用图遍历状态。**

前一轮697.800156ms的精确pilot+完整重扫是单独建模的执行方式，**不是当前机制
实验实际执行了两次扫描**。同样，ANN约88微秒的付费余量只适用于已审查的
“完整pilot+完整后续调用”成本模型，不能推广为所有缓存/续搜实现的上限。
旧固定调用的搜索前oracle也是以旧调用成本为前提；新后端改变成本后需要重新评估。
这些是适用范围澄清，既有MILP结果不作改写。

## 1. 已经复用了什么

| 工作 | 当前精确机制v1 | 当前ANN v1 |
|---|---|---|
| 查询投影 | 每次流水线一次 | 每次流水线一次 |
| 投影全库扫描 | 一次，提前取top256 | 无全库扫描，调用HNSW |
| 后续候选 | 切取已保存的精确前缀 | 保留旧池，补充新候选；不是嵌套精确前缀 |
| 候选投影距离 | 从同次扫描的前缀距离复用 | host float64精算按ID缓存 |
| 原空间评分 | 只计算新增候选 | 只计算新接受候选 |
| 图遍历/内部距离 | 不适用 | 每次search重新开始，没有查询级续搜状态 |

直接证据：

- [exact_policy.py 的 pipeline](../mechanism/tls_rag_step5_exact_policy.py)：
  `scan.search(qp, maximum)`位于预算循环之外；循环仅传入`rr[:budget], dd[:budget]`。
  `PrefixSession.expand`验证前缀嵌套，并只为`new`候选计算原空间距离。
- [ExactScan.search](../mechanism/tls_rag_step5_audit.py)：按块计算float64直接差平方距离，
  维护最大候选集合，未保存全库距离数组。
- [CandidateSession.expand / HnswCandidateIndex.search](../src/tri_rag_harness/tls_rag_step5_ann.py)：
  每次扩展调用FAISS search；projected_cache和original_cache保留外部计算结果。
- [旧检索计时说明](RETRIEVAL_LATENCY.md)和
  [旧benchmark源码](../src/tri_rag_harness/retrieval_benchmark.py)也明确区分一次扫描复用
  与两次扫描对照。旧合成数据性能不能移作本次文本语料的性能证据。

因此，给当前精确流水线再加一层“复用pilot候选”的缓存，不会消除另一遍全库扫描：
这遍重复扫描本来就不存在。可改进对象是**提前支付的最大预算选取工作**。

## 2. 精确后端：一次计算距离，延后选取更大M

有价值的待测布局是：扫描全库一次，保存每项已计算的投影距离；先选pilot32，
需要扩展时从同一距离数组继续选64/128/256，不再次读取全库向量或计算距离。

对固定查询，按`(float64平方L2距离, 稳定字符串ID)`构成全序。
只要保存的距离位值、ID和边界处理不变，从该全序取前M与原精确结果一致。
因此这条路线有清楚的结果等价性目标。它不能免除取得精确pilot所需的全库扫描；
在没有另外证明的有效剪枝时，所有N个距离仍要计算。

代价及公平性必须一起计入：

- N=1,000,000时，float64距离数组本体为8,000,000字节，约7.63MiB/并发查询；
  不包含行索引、partition临时数组、分配器和并发开销。另一个int64全库索引数组
  也需8,000,000字节，不能称总增量只有8MB。
- 保存数组增加写入和内存管理成本。多次完整partition可能重复扫描距离数组；
  应比较缓存后重新选取与可复用partition边界的方式，不能默认选取免费。
- 当前前缀的特征接口仍只接收当前候选，不能借内部全距离缓存读取未来候选信息。
- 相同缓存/选取优化也要给固定预算和查询无关混合对照。不能只优化自适应方法。

已有Selection256分项均值提供定位，不是新布局的计时结果：

| 固定M | 全流水线 ms | 扫描+选取 ms | 其中选取 ms |
|---:|---:|---:|---:|
| 32 | 619.186165 | 618.934062 | 25.907190 |
| 64 | 623.956410 | 623.601130 | 26.884572 |
| 128 | 626.569655 | 625.917921 | 29.174917 |
| 256 | 630.636599 | 629.468884 | 33.798670 |

来源：[已保存成本证据](step5_tri_feature_cost_review_evidence.json)的
`selection_cost_audit.component_means_ms`。选取是“扫描+选取”的子项，不可重复相加。
256与32的选取差为7.891480ms，但这既不是新布局的净节省，也不是通用上限：
新布局的缓存成本、多次选取以及固定对照的共同优化均未测量。
约600ms的主要扫描工作仍然共享且难以用M控制，所以候选数降低不等于同比加速。

## 3. HNSW：候选复用与真正续搜是两件事

核对本项目固定的FAISS **v1.8.0**，不是当前最新版：

- [`IndexHNSW::search / hnsw_search`](https://raw.githubusercontent.com/facebookresearch/faiss/v1.8.0/faiss/IndexHNSW.cpp)
  在一次调用中建立结果处理器、VisitedTable及距离计算器。
- [`HNSW::search`](https://raw.githubusercontent.com/facebookresearch/faiss/v1.8.0/faiss/impl/HNSW.cpp)
  从入口做高层下降，建立局部候选堆，结束时推进visited代号。
  普通search返回结果，没有向本项目交出可恢复的查询状态。
- 同一实现的`search_level_0`可接受起点，但重新创建候选堆；这是起点复用接口，
  不能直接视为保留整个搜索现场的resume。

判断如下：

1. **外部候选与原空间距离缓存：已经存在。** 不应再次把这部分记成待实现收益。
2. **FAISS内部点到查询的距离缓存：可能研究。** 即使再次遍历图，也可能避免重复
   距离核计算；仍有访邻居、堆操作与缓存查找成本。需要测量重复访问量及缓存费用。
   内部float32距离不能直接代替科学特征所用的host float64距离。
3. **完整续搜：不能靠保存最终top64完成。** 需要visited状态、未扩展队列、距离缓存
   和相关停止状态；小ef搜索已丢弃的候选还要处理。直接扩大堆或从旧结果热启动，
   未证明等价于从头用更大ef搜索，可能改变路径、候选和质量。

现有记录没有保存足以复建这些状态的逐节点轨迹。旧候选集合重叠率即使很高，
也不能据此算出内部距离重复率或实际续搜加速。不能从旧质量记录推造新后端收益。

## 4. 只消除重复pilot，可以改善多少旧成本模型

在旧Tune2048的.90目标、原单次调用成本和质量表保持不变的条件下：

- 完美pilot+完整重搜oracle：2.044292497ms/查询；
- 完美搜索前选一次调用oracle：2.033441818ms/查询；
- 差值：`(11/2048) * 2.020199221 = .010850679ms/查询`。

因此，在这个特定模型中，理想地消掉扩展查询重复的完整pilot费用，余量从
.088064200ms扩大到.098914880ms，约88→99微秒。两者都假设决策信息免费。
这不是已实现缓存的性能，也不证明新的续搜后端最多只能省这些时间；后端变了，
需要新成本与质量记录。它只说明：**单独去掉该模型中的第二份pilot收费，不能
自动产生很大的收益空间。** 所有数字来源于
[原成本筛查证据](step5_action_cost_screen_evidence.json)，未重新求解或改动原记录。

## 5. 推荐次序和停止条件

1. 优先评估精确距离缓存+延迟选取的小规模本地CPU基准，先检验同值、距离计数、
   完整开销与峰值内存，不训练预测器、不接Tri。它的等价性目标明确，实现负担
   小于自定义HNSW续搜。保持32/64/128/256与现有几何/精度/字符串ties不变。
2. 若缓存自身或扩展选取吞掉收益，停止该执行布局；若有收益，先将同样优化施于
   固定对照，再计算免费oracle与付费特征余量。只看旧完整调用表不足以判断新布局。
3. HNSW若继续研究，应先做CPU内部距离/重复访问探针，之后再决定是否值得维护
   新续搜内核。不能把它作为无需验证的现成FAISS开关。
4. 只有在完整付费空间为正之后，才讨论收益预测、Tri门控或教师蒸馏。不能先训练
   更好的预测器，再期待它补偿无法避免的扫描成本。
